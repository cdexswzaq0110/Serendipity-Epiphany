# Acquire — 習得

**這是學習新技能的地方。** 其他 skill 處理已知的問題；這個 skill 處理「還沒有 skill 的問題」，
並且讓那一次的經驗有機會變成下一次的能力。

不是保證做對。是保證**做法有紀律、結果有證據、經驗不白費**。

---

## 什麼時候不是這個

| 情況 | 該用 |
|---|---|
| 領域熟，只是需求還講不清楚 | `se-clarify` |
| 領域熟，但工作大到講不出「做完長什麼樣」 | `se-discovery` |
| 領域熟，已經知道要切成哪幾片 | `se-design` |
| **領域本身是新的**——沒有任何 skill 覆蓋它 | **這裡** |

判準一條：**把任務講給既有 skill 的 description 聽，有沒有任何一個會說「這是我的」？** 沒有，就是這裡。

---

## 第 0 步：承認不知道（自我理解）

```bash
python .claude/tools/capabilities.py
```

讀「我會什麼」與「結構上做不到的」兩段，然後**明說**：

> 這個任務不在任何既有 skill 的範圍內。以下是在沒有現成能力的情況下的做法，
> 結論的證據等級一律從「推論」起算，直到驗證過。

**這一步不能省。** 在新領域裡最貴的錯誤不是做不到，是**假裝做得到**——用熟悉領域的
自信去處理陌生領域，然後把推論寫成已確認。`evidence-grades` 在這裡最重要。

## 第 1 步：遷移——別的專案學過什麼

```bash
python .claude/tools/lessons.py list --tag <這個領域的關鍵字>
```

再讀本專案 `docs/lessons/INDEX.md`。**找的是類別，不是同一個問題**：
新領域的坑，常常是舊領域某一類坑的新形狀。

例：一則「判定條件錯的時候，失敗的形狀是集體沉默」的教訓，在 eval、在 plugin 載入、
在 ML oracle 上都成立過——它對一個全新的領域一樣成立。

## 第 2 步：借最近的鄰居

新領域幾乎不會跟所有已知領域都無關。找**結構最像**的既有 skill，借它的骨架：

| 新任務的形狀 | 借誰的骨架 |
|---|---|
| 有資料、要預測或分類 | `se-ml-lifecycle` 的 Gate 順序（先驗切分再碰模型） |
| 要設計一個系統 | `se-system-design` 的先估數字再擺元件 |
| 要改一段既有的東西 | `se-minimal-change` 的階梯 |
| 東西壞了要修 | `se-debug` 的「先做出會變紅的回饋迴圈」 |
| 完全沒有鄰居 | 用 `se-clarify` 把「做完長什麼樣」問到可判定 |

**借的是紀律，不是內容。** ML 的 Gate 順序可以用在任何「先驗證評估方法再優化」的領域。

## 第 3 步：先定驗證，再動手

**在新領域裡，這一步比任何其他步都重要。** 開始做之前，寫下：

1. **做完長什麼樣**：一個可以判定的條件，不是「感覺可以」
2. **怎麼驗證**：跑什麼、看什麼、得到什麼算過
3. **怎麼知道自己錯了**：最可能的失敗形狀是什麼

寫不出第 2 條，代表你還不懂這個領域到能動手的程度——回第 1、2 步，或問人。

**新領域幾乎都帶著新工具。** 要用的 CLI、套件、API 這台機器有沒有、能不能跑，
交給 `se-preflight` 查——它是這一步的下游，不是替代品。直接跑 `<tool> --version`
只回答「有沒有」，不回答「壞了用什麼替代」。

## 第 4 步：做，然後用證據宣告完成

照 `core-rules` 第 4 條：沒跑過的檢查不寫成通過。

新領域的特殊處：**你的判定條件本身也可能是錯的**（見 `docs/lessons/0005`）。
第一次結果不合預期時，先懷疑判定，再懷疑做法。

## 第 5 步：把經驗留下來

分兩條路，由結果決定：

### 做法有效、而且下次還會用 → 寫成**候選 skill**

```text
.claude/skill-candidates/<名稱>/
├── SKILL.md
└── evals/trigger-cases.md
```

- `SKILL.md` 照一般 skill 的格式寫，frontmatter 加 `validated:`，填**這一次在哪裡成功、產出是什麼**
- `trigger-cases.md` 的第一條，用**使用者這一次的原話**，來源標 `user-prompt`

**候選不會自動載入。** 要升級成正式 skill，得過 `promote_skill.py` 的四道閘——其中一道是
**至少 3 條獨立來源的觸發案例**。這一次只貢獻 1 條。

**所以一個做法要在真實工作裡重複出現至少三次，才會成為正式能力。**
這是刻意的：一次成功可能是運氣，三次是模式。

下次同類任務出現時，先看 `promote_skill.py --list`——如果已經有候選，**用它、補一條案例**，
而不是再寫一個新的。

### 做法無效 → 寫成 Lesson（`outcome: dead_end`）

「試過 A，因為 B 所以不行」跟成功的做法一樣有價值。走 `se-epiphany` 的捕捉模式。

### 其中有跨領域都成立的東西 → 上架全域帳本

如果這次撞到的東西，你**在另一個專案也撞過**：

```bash
python .claude/tools/lessons.py promote docs/lessons/<那則>.md \
  --seen-in "<這個專案>" --seen-in "<另一個專案>" --evidence "兩邊各自發生的具體描述"
```

只在一個專案撞到的，留在專案帳本。**一次不算遷移。**

---

## 邊界

- **不直接寫進 `skills/`。** 一律先進 `skill-candidates/`。直接寫進去就繞過了驗證。
- **不因為做完了就寫候選。** 只有「下次還會用到、而且做法有效」的才寫。
- **不假裝熟悉。** 第 0 步的明說是必要的，不是禮貌。

## 完成條件

- 第 0 步的「沒有現成能力」已明說
- 第 3 步的驗證條件已寫下且實際跑過
- 結論的證據等級誠實標示（新領域預設「推論」）
- 經驗已留下：候選 skill、dead_end lesson、或明說「這次不值得留」與理由
