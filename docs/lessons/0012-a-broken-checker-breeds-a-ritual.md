# 壞掉的檢查器會養出一個儀式

## 觸發情境

發現自己（或 agent）有一個**每次都做**的小動作：改完檔順手正規化、commit 前順手清快取、
跑測試前順手重裝依賴。做的時候理由很清楚，但已經想不起來上一次它真的有用是什麼時候。

## 領悟

`mine.py` 第一次在真實逐字紀錄上跑，動作礦脈的前幾名裡有一個：

> `sed -i 's/\r$//' <f>`——**89 次以上**，橫跨 2 個 session，每次常常一口氣處理好幾個檔。

背後的信念是「Write／Edit 工具會寫出 CRLF，commit 前要轉回 LF」。逐一驗證：

| 信念的零件 | 實測 | 證據 |
|---|---|---|
| Write 工具寫出 CRLF | **假**：0 個 CR 位元組 | Python 位元組計數；`xxd` 只見 `0a`【已確認】 |
| Edit 工具寫出 CRLF | **假**：CR 0、LF 4 | 同上【已確認】 |
| 不轉的話 commit 進去會是 CRLF | **假**：`.gitattributes` 是 `* text=auto eol=lf`，git 自己會轉 | `git ls-files --eol`：全部 `i/lf`【已確認】 |
| 「檔案裡有 CR」這個觀察 | **檢查器壞了**：`grep -c $'\r'` 對沒有 CR 的檔回報「每一行都有」；換成 `grep -c "$CR"` 則對真的 CRLF 檔回報 0 | 對照組：一個真的 CRLF 檔、一個沒有 CR 的檔【已確認】 |

**整條鏈的源頭是一個兩個方向都會錯的檢查器。** 它每次都說「有 CR」，於是轉換變成了儀式；
轉換之後再檢查，檢查器的答案不一樣了（因為換了寫法或換了檔），看起來就像「轉換有效」。

這是 G0001／L0005 在本地第三次發生：系統說壞了，第一個嫌疑犯是判定條件。
這次不同的是，**它不是被人注意到的，是被採礦挖出來的**——一百次重複自己浮上來，才有人回頭問為什麼。

## 為什麼會撞到

儀式的成本低到不會有人去質疑：一次 `sed` 不到一秒。可是它每次都在，而且每次都附帶一個錯的世界觀
（「這台機器的工具會寫出 CRLF」），那個世界觀會影響其他判斷——例如把 L0004 的 PowerShell 編碼問題
跟它混為一談。

## 下次怎麼做

1. **每個重複動作都有一個信念，先把信念寫成一句可以驗證的話。** 「Write 工具會寫出 CRLF」可以驗證；
   「這樣比較保險」不行。
2. **驗證要用跟原本不同的量法，並且帶對照組。** 同一個檢查器再跑一次只會得到同一個錯。
   一個已知是、一個已知否，量法兩個都答對才算數。
3. **在這台機器上量 CR：** Python 讀位元組、`git ls-files --eol`、`xxd`。**不要用 `grep`**。
4. **信念被推翻就停掉動作，並留紀錄**——不然下一個 session 會從同一個壞檢查器重新學回來。

## 失效條件

- 若 `.gitattributes` 的 `eol=lf` 被移除，第 3 列不再成立，要重驗。
- 若換機器或換 Git 版本，`grep` 的行為要重新對照（這裡的結論只對這台 Git for Windows 成立）。
