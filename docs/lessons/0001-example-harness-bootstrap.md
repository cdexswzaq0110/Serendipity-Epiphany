# 常駐規則只會單向長大，要有機制才刪得掉

## 觸發情境

準備新增一條 `rules/` 常駐規則，或把一套配置帶到新專案、新機器上開始用。

## 領悟

**常駐面沒有機制的話，只會單向長大。**【推論：依這套配置自己的分類表——19 條常駐項目裡有 4 條標著「未登記」，也就是連我自己都填不出它為什麼存在】

而且長大的方式很隱蔽：每一條單獨看都很有道理，是加總起來才出事。

## 為什麼會撞到

原本的假設是「規則越多越安全，反正只是幾行字」。

錯在兩件事：

1. **常駐內容不是免費的。** 它每一輪都在花 token 與注意力，而且會壓縮解空間——規則之間互相牴觸時，模型會猶豫。
2. **補丁型規則有保存期限。** 它是為了修某個模型版本的行為而寫的。模型換代之後，它從「修正」變成「多餘的約束」，但**沒有人會主動去刪一條看起來很有道理的規則**。

第二點是關鍵。加規則感覺安全，刪規則感覺有風險，於是沉積層越疊越厚，最後你必須挖穿好幾層才找得到哪些還活著。

## 下次怎麼做

**每條常駐規則都必須填得出「因為模型反覆犯什麼錯才存在」。填不出來就不准加。**

分兩類處理：

- **補丁**（修模型的錯誤行為）→ 每個模型大版本重驗，沒證據就刪
- **意圖**（我自己的方法論、決策邊界）→ 不消融

判準一句：刪掉它，壞的是**模型的行為**，還是**這套配置的目的**？

消融流程（每個模型大版本或滿六個月）：

1. `rules/` 暫時只留 `golden-rules.md`
2. 跑三個最常做的任務
3. 只記**反覆出現**的同一種失敗（一次性失誤不算）
4. 一次加回一行，在 `.claude/ABLATION.md` 登記證據
5. 沒加回的不留

**不要憑感覺刪，要全部拿掉再逐條加回來。** 憑感覺刪會保留最順眼的，而不是最有用的。

## 失效條件

- 模型大版本更新後這則要重跑——消融的結論綁定在特定模型版本上。
- 若未來有自動測量常駐面效果的機制（自動 A/B 跑 eval），這則的手動流程該被那個機制取代。
- `.claude/ABLATION.md` 若被刪除或改變結構，這則指向的流程需要重寫。
