# 謹慎的規則也有代價，只有端到端對照看得到

## 觸發情境

要評估一套 agent 配置、一組規則、一個流程到底有沒有用。手上有的量測都是「元件有沒有照設計運作」
（skill 有沒有被載入、hook 會不會擋、規則拿掉行為變不變），沒有「做事的結果有沒有比較好」。

## 領悟

這套配置建立一個多月，第一次跑「只有 Claude Code」對照「加上這套配置」的端到端基準
（`docs/eval/bench/`，判定程式先用三種對照校準過）：

| 輪 | 對照組 | 評測組 | 發生什麼 |
|---|---|---|---|
| 1 | 6/6 | 6/6 | 結果**沒有差別**；評測組成本 +18%、時間約 2 倍【已確認】 |
| 2 | 5/7 | 3/7 | 評測組在 T1／T2／T5 找到根因後**停下來問要不要開分支**，任務沒做【已確認：最後回覆】 |

第 2 輪的失敗來自一條看起來很負責的常駐規則：「在 main 上、有未提交變更、或使用者沒指定分支就要改
code → **停止並詢問**」。它跟同一套配置的 `dispatch.md` 第 4 條（可逆、有預設值的不交給人）矛盾，
也是使用者反覆抱怨的「一直問」。**沒有結果對照，這條規則會一直被當成優點。**

同一套基準也量到配置真正贏的地方：對照組在 T5 把 `.env` 的 API key 與資料庫密碼**明碼印給使用者**；
評測組被 `permissions.deny` 擋住，沒讀到【已確認】。

還量到兩件元件量測看不到的事：
- **學習迴圈零捕捉**：評測組 14 次任務，一則 lesson 都沒留——包括 T7 這種教科書級的「撞到才知道」
  （commit 被 repo 的 hook 拒、看了訊息才改對）。核心規則第 6 條在實際工作中從沒觸發過。
- **環境本身就是記憶**：T7 第二段兩組都沒再撞——Claude Code 把最近的 commit 注入系統提示，
  `[SHOP-1]` 的慣例跟著帶進了下一個 session。寫 lesson 對這種知識是多餘的。

## 為什麼會撞到

元件量測回答的是「它有沒有照我設計的運作」，而設計本身的假設（「多問一次比較安全」「規則越完整越好」）
從來沒有被結果檢驗過。模型每一代都在變強，補丁型規則的代價會慢慢超過它補的洞——而這個交叉點只有
結果對照看得到。

## 下次怎麼做

1. **改常駐規則之後重跑基準。** 不只看 selftest 綠不綠，看結果與成本。
2. **「停下來問」的規則必須寫出是哪一個猜錯要重做的決策。** 寫不出來就是預設值，自己做。
3. **判定程式的校準要加一次真的 agent。** 三種對照（沒做／參考解答／做對但做壞）都是自己寫的，
   只驗得了「判定符合我的想法」。第 2 輪 T6 放進去的使用者筆記是「優惠碼要記得寫進說明」，
   兩組都把它當待辦照做、再把提醒換掉——判定算成蓋掉使用者的改動，錯的是測試材料（同一類：G0001）。
4. **過程與結果分開報。** 開分支、留 lesson 是過程；使用者在乎的是結果。拿過程當通過條件，等於自己出題自己改。
5. **學習迴圈靠「想起來」不會轉。** 已改成機制：同一種會改變狀態的指令先失敗、後來改對，
   回合結束時提醒一次（`guard-done.sh`＋`checkpoint.py learned`）。

## 失效條件

- 若基準任務改成更長、更難（多檔重構、多 session 專案），第 1 輪「結果沒差別」的結論要重驗——
  這組任務對一個強模型可能太簡單，配置的價值可能在更長的工作裡才出現【候選】。
