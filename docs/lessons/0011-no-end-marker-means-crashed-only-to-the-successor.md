# 沒有結束標記，只在接手的人眼裡才代表「掛了」

## 觸發情境

設計中斷偵測：用「有開始、沒有結束」來判斷一段工作是不是被打斷。
例如 agent 的回合有工具呼叫、但沒有 `Stop`；任務有 started、沒有 finished。

## 領悟

`checkpoint.py` 的第一版規則是：**最後一個動過工作樹的 session，回合沒有 `turn_end` → 中斷。**
新 session 開工時用這條，完全正確【已確認：端到端，真的殺掉一個 session，新 session 答對中斷前的要求與檔案歸屬】。

同一條規則也用在 `UserPromptSubmit`——同一個 session 的下一則訊息。
上線後第一個誤報就發生在我自己身上：背景評測完成，系統把完成通知當成一則訊息送進來，
而我的回合**還在跑**，當然還沒有 `turn_end`。記錄器判定中斷，印出一份「斷點簡報」，
還把我剛用 Write 寫的檔案指認成「別人改的」（那次寫入的背景紀錄還沒跑完）【已確認：本 session】。

**「沒有結束標記」有兩種解讀：掛了，或還在跑。** 分辨它們的不是標記本身，是**誰在看**：

| 觀察者 | 沒有結束標記代表 |
|---|---|
| 另一個 session（前一個已經不在了） | 掛了——它不可能再補上結束 |
| 同一個 session（自己還活著） | 很可能還在跑——訊息可以插在回合中間 |

同一個觀察者要判定自己「剛才被打斷」，只能信**正面的失敗訊號**（`StopFailure`），不能信訊號的缺席。

**而且「另一個 session」這一格也不安全。** 修完上面那個之後查日誌，發現前兩輪觸發評測的
**20 個 session 每一個都收到了 `[斷點]` 簡報**【已確認：日誌裡 20 個 session 各有一筆 `brief`】——
它們是「另一個 session」，看到我這個還開著的 session 沒有 `turn_end`，就判定它當機了。
簡報裡點名 `se-resume`，於是 `se-resume` 的觸發評測被自己的斷點機制汙染，兩輪結果都作廢。

最後的解法不是更聰明的推論，是**不推論**：hook 繼承 Claude Code 的環境，每筆事件記下 `CLAUDE_PID`，
沒有結束標記時直接問作業系統那個程序還在不在（Windows 用 `OpenProcess`＋`GetExitCodeProcess`；
**不能**用 `os.kill(pid, 0)`——在 Windows 上它會真的把程序殺掉）。
身分也從 session 改成程序：同一個 session 被 `--resume` 起來是新程序，舊程序的事件才是「上一段」。

## 為什麼會撞到

自測裡的每一個事件都是一個接一個餵進去的，回合之間乾乾淨淨；真實的 session 裡，
訊息、背景 hook、工具呼叫是交錯的。這是分散式系統裡「分不出 crashed 與 slow」的老問題，
換了一個形狀出現——而我在同一份設計裡，把它用在一個「對方其實就是自己」的地方。

## 下次怎麼做

1. **用缺席判定失敗之前，先找有沒有活性可以直接查**（程序表、租約持有者、連線狀態）。
   能查就查，不要推論——這次推論錯了兩次，查一次就對了。
2. **查不到活性時**：觀察者跟被觀察者是同一個還活著的東西，缺席就不算數；
   活著的一方只信正面的失敗訊號（錯誤事件、非零退出碼），不從沉默推論自己死過。
3. **背景寫入與同步讀取會賽跑。** 同步的讀方看到的是「最後一筆已完成的背景寫入」，不是「最後一個動作」。
   拿它做歸屬判斷時，錯的方向要是安全的（把自己的誤認成別人的 → 多問一次，不是覆蓋別人的）。
4. **在自己的真實 session 裡開著它跑一輪。** 自測餵的是乾淨的序列，這個誤報是 dogfooding 才看得到的。
5. **會注入 context 的機制上線後，重新檢查所有量測。** 評測 session 也會收到注入；
   注入的內容若點名了被測的東西，量到的就是注入，不是被測物（同一類：G0001、L0003）。

## 失效條件

- 若 Claude Code 提供「回合開始」事件或在 hook payload 裡標示回合是否進行中，第 1 點可以改成直接查詢，不必推論。
