# 量尺自己要先被量：eval 跑出來的第一個數字通常在量工具，不是量系統

## 觸發情境

要建立任何「模型行為」的評測——skill 觸發、路由、prompt A/B。第一次拿到數字的時候。

## 領悟

**第一版 eval 跑出 1/8，第三版跑出 4/4，中間沒有改過任何一行被測的東西。** 差別全在量尺。

三個坑，每一個都會產生「看起來像系統壞掉」的數字：

1. **案例不自足。** 案例照「真實說過的話」寫（「這東西做得出來嗎」「改完了幫我檢查一下」），但真實對話有前文，評測的每個 session 從零開始。模型回「這東西指的是什麼」而不是載入 skill。16 次有 12 次什麼都沒載入。**代詞在乾淨 session 裡沒有指涉對象。**
2. **答案外洩。** 案例集就存在被測的 repo 裡。給了 Read/Grep 之後，模型 `grep csv` 直接搜到 `trigger-cases.md`，看見「該載入」欄。【已確認：B1 transcript 有那次 grep】
3. **工具限制改變行為。** 收回 Read/Grep 擋住外洩，但**動作型案例**（修 bug、加欄位、review）失去執行條件——模型只能回「把檔案給我」，從頭到尾不需要 skill。判成 FAIL 的是工具被拔掉的結果，不是路由。

第 2 與第 3 是**同一個取捨的兩端**，在同一個 repo 裡無解。要兩者兼得，evaluation fixture 必須跟被測配置分家。

## 為什麼會撞到

因為「先建量尺，再動被量的東西」這條原則，只寫了順序，沒寫**量尺本身也要有驗收條件**。

第一版量尺是照著「怎麼判 PASS/FAIL」設計的，完全沒問「這個設計會不會自己製造 FAIL」。結果第一個數字 1/8 看起來像是路由嚴重失效——如果當場相信它，接下來就會去「修」一個沒有壞的東西。

## 下次怎麼做

拿到第一批數字時，**先看失敗的形狀，不要先看比例**。

- 大量案例落在**同一種失敗**（例如全部「沒載入任何東西」）→ 幾乎一定是量尺，不是系統。真實的路由錯誤是**載入了錯的那個**，不是集體沉默。
- 每個案例必須自足：讀完那一句就知道在講什麼，不依賴任何前文。
- 評測資料要放在被測系統**讀不到**的地方，或者關掉搜尋工具。
- 動作型案例與判斷型案例要分開設計——前者需要真實的執行標的，後者不需要。
- 只在測「決策」時才可以拔工具。測「行為」不能拔。

## 失效條件

- 改用真正隔離的 fixture（把配置複製到不含案例集的暫存專案）之後，第 2、3 點的取捨消失，本則的一半該改寫。
- 若 Claude Code 提供官方的 skill 觸發評測機制，本則的手動設計細節被取代。
- 案例集若改成「刻意模糊」的輸入來測邊界，第一條（案例必須自足）需要重新表述——那時模糊是刻意的，不是缺陷。
