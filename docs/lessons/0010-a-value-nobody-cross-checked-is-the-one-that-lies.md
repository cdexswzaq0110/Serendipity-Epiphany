# 會說謊的不是手寫的那段，是沒被對照過的那段

## 觸發情境

一個系統在描述自己——能力清單、健康檢查、狀態報告——而你要決定哪些部分可以信。
特別是同一個事實（檔案數、版本、狀態）被兩個以上的元件各自算出來的時候。

## 領悟

L0008 說「自我描述裡手寫的那段會說謊，生成的不會」。**錯了。**

`capabilities.py` 的全域帳本計數是生成的，一直是錯的：它找 `[0-9]*.md`，
`lessons.py` 寫的是 `G0001-*.md`，所以永遠回報 0【已確認：修正前 0、實際 1】。

**它看起來是對的，原因有兩個：**

1. **驗證的時間點早於會暴露它的狀態。** 第一次跑 `capabilities.py` 時全域帳本是空的，
   0 是**正確答案**。G0001 之後才上架（13:26），沒有人重跑對照。
2. **0 是最像真的錯誤數字。** 它不會讓人覺得「數字對不上」——一個新建的帳本本來就可能是 0。

**它是怎麼被抓到的**：把配置帶進 churn-guard 後，同一個畫面上
`recall-lessons.sh` 說「跨專案 1 則」、`capabilities.py` 說「全域 0 則」。
兩個**各自實作**的計數並排出現，才露餡。

L0008 抓到的那個手寫錯誤，也不是因為它是手寫的——是因為我**去 DESIGN_RATIONALE 對照了**。

## 為什麼會撞到

同一個量由兩處各自計算，中間有一條沒寫下來的格式契約（全域檔名以 `G` 開頭）。
寫 `lessons.py` 時知道這條，寫 `capabilities.py` 時用了專案帳本的習慣（數字開頭）。
兩邊各自的自測都會過——各自的世界裡都是對的。

## 下次怎麼做

1. **信任軸是「有沒有被獨立來源對照過」，不是「手寫還是生成」。**
2. **同一個量有兩處在算，要嘛讓一處讀另一處，要嘛寫一條測試比對兩者。**
   這次補的是後者：selftest 在上架一則之後，檢查 `capabilities.py` 數到 1。
3. **測試要測「狀態變了、數字跟著變」，不是只測一個快照。** 空帳本上的 0 是對的，
   上架一則之後還是 0 才是錯的。只在初始狀態跑過的檢查，對「會長大的東西」什麼都沒證明。
4. **看到 0、空、預設值時多問一句**：這是真的沒有，還是根本沒數到？（同一類：G0001）

## 失效條件

- 若全域計數改為直接呼叫 `lessons.py` 的函式（單一實作），第 2 點的具體案例消失，原則仍成立。
