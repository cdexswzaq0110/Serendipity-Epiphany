# 系統說「壞了」的時候，第一個嫌疑犯是你的判定條件

## 觸發情境

你寫了一段檢查去判斷某個系統有沒有正常運作，而它回報「沒有」。
特別是：那個系統的輸出格式你不是完全熟悉。

## 領悟

**同一輪工作裡，這件事發生了四次，四次都是判定條件錯，不是系統壞。**

| # | 我的判定說 | 實際上 |
|---|---|---|
| 1 | skill 路由 1/8，嚴重失效 | 案例用了代詞，乾淨 session 裡沒有指涉對象 |
| 2 | 雙軸 review 沒有並行派發，是執行模型缺陷 | headless 環境**全程**不批次任何工具呼叫，量不到 |
| 3 | 模型超過了 oracle 天花板 | 我把「當週 hazard」當成「未來 30 天標籤」的上界，定義就錯了 |
| 4 | plugin 載入 0 個 skill，連官方預設佈局都失敗 | plugin skill 帶命名空間 `plugin-name:skill-name`，我用了 `startswith('se-')` |

第 4 個最能說明問題：我連續測了三種佈局，全部回 `no`，於是準備去重構目錄結構——
**差一步就要為了一個不存在的問題動整個 repo。** 印出完整清單才發現名字前面多了前綴。

**共同形狀**：判定條件是我寫的，被判定的輸出格式是我猜的。猜錯的時候，
錯誤會以「系統壞了」的形式出現，而且**看起來有憑有據**——有數字、有多次重複、
甚至有跨三種配置的一致失敗。

## 為什麼會撞到

因為「檢查失敗」和「系統失敗」在輸出上長得一模一樣，而人的預設歸因是後者。

更危險的是**一致的失敗**。第 4 次我測了三個佈局全部失敗，那個一致性讓我更確信是
系統問題——但它其實只證明了我的判定條件在三次裡都一樣錯。**一致性不是正確性的證據，
它只排除了隨機。**

## 下次怎麼做

1. **先印出原始輸出，再寫判定。** 不要用 `if X in list` 去問一個你沒看過的 list。
   第一次一定要 `print(list)`。
2. **失敗的形狀比失敗的比例重要。** 全軍覆沒（包括該過的對照組）幾乎一定是判定；
   真實的系統缺陷通常是**部分**失敗。
3. **判定要有第三個檔位。** PASS／FAIL 兩檔會把「測不到」誤報成「壞掉」。
   第三檔（`unmeasured` / `INCONCLUSIVE`）必須由**儀器自檢的數字**決定，不是事後解釋。
4. **對照組必須包含一個「已知會過」的案例。** 第 4 次如果我先測一個確定能載入的
   內建 skill，會立刻發現名字格式不對。

## 失效條件

- 若判定改由系統本身提供的官方 API 回報（而不是自己解析輸出），第 1、4 點失效。
- 若被測系統的輸出格式有正式 schema 且已驗證，本則降為低優先。
- 第 3 點若被 `run_eval.py` 的三檔位機制吸收成常規做法，這一條可以從 lesson 移除。

## 尚未驗證

**這則還沒做過 leave-one-out。** 依 `se-epiphany` 的四關，它過了 SCAN 與 MUTATE，
**沒過 VALIDATE**——沒有證據說「把這條寫進常駐規則會減少這類錯誤」。

所以它留在帳本，不升級。`validated` 欄位空著就是這個意思。
