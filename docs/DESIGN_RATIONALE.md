# 設計理據

**改動任何一條規則之前，先讀它為什麼存在。**

刪掉一條你不知道它在解什麼問題的規則，是這套配置最容易犯的錯——那條規則通常是某次很貴的失敗留下來的。

---

## 十條核心信念

這套配置的每一個機制都從這十條裡長出來。

### 1. 證據等級是第一公民

模型最貴的失敗不是「不知道」，是**把推論寫得像事實**。

讀者無法從措辭分辨「我跑過」與「我覺得應該」，於是把兩者當同一件事用。等到發現的時候，那個推論已經被三份文件引用過了。

所以每個會被拿去做決定的結論都帶等級：`已確認`／`推論`／`候選`／`未知`／`未驗證`。而且**不可升級也不可降級**——沒有新證據，時程壓力不能把候選變成已確認。

→ `rules/evidence-grades.md`

### 2. 確定性工程 × Agent

**不能出錯的步驟，用程式或明確清單保證；動態決策與動態取材才交給模型。**

純語言驅動的流程沒有硬約束：大型變更時會「抄捷徑」只看部分檔案、回報的位置會漂移、換個措辭品質就變。

所以：檔案選擇、規則比對、Gate 判定這類**必須不能錯**的部分寫成清單或程式；判斷、取捨、深挖這類**需要彈性**的部分留給模型。

→ `se-skill-authoring` 的出貨門檻第一條、`se-ml-lifecycle` 的 Gate 設計

### 3. 常駐面要有失敗證據

常駐內容不是免費的：每一輪都在花 token 與注意力，規則互相牴觸時模型會猶豫。而補丁型規則有保存期限——模型換代後從「修正」變成「多餘的約束」。

沒有機制的話，常駐面只會單向長大：加規則感覺安全，刪規則感覺有風險。

所以每條常駐規則都要填得出「因為模型反覆犯什麼錯才存在」。**填不出來就改寫成 Skill 按需載入。**

→ `.claude/ABLATION.md`、`docs/lessons/0001`

### 4. 先爬最小實作階梯，但五件事不得省略

最好的程式碼是沒寫的那行。七階梯：不用寫 → 已經有 → 標準庫 → 平台原生 → 已裝依賴 → 一行 → 最小可動。

但階梯**在理解問題之後才跑，不是取代理解**。一個你不理解的小 diff 不是最小變更，是第二個 bug 穿著效率的外衣。

而且五件事永遠不得省略：理解問題 · 信任邊界的輸入驗證 · 會造成資料遺失的錯誤處理 · 安全 · 無障礙。

→ `se-minimal-change`

### 5. Finding 是待驗證的主張，不是命令

Review 提出的問題是一個**需要驗證的主張**。實作者必須重現它，成立就修，不成立就提出可重現的反證。

反過來，Reviewer 不能因為 Finding 是自己提的就拒絕撤回。

雙方沒有新證據時停止爭辯，把爭點交回上層。**不得叫第三個模型來投票**——投票不是證據，要的是能辨別爭議的最小測試。

→ `se-two-axis-review`

### 6. 兩軸不合併

一份變更可以過一軸卻掛另一軸：遵守了每條規範但做錯東西，或完全照規格做了但破壞專案慣例。

**「規範全過但做錯東西」是最貴的失敗。** 合併排名會讓 8 個小規範問題把 1 個致命的規格問題壓下去。

所以 Spec 軸與 Standards 軸派成互相隔離的 Thread，首輪不互看，分開報，不跨軸排名。

→ `se-two-axis-review`

### 7. 共享語言先於程式碼

Agent 被丟進一個專案、被要求邊做邊猜行話，於是用 20 個字講一件 1 個字就講得完的事。

一份 `CONTEXT.md` 省的不只是 token：變數與函式命名一致、codebase 更好導航、需求討論與程式碼用同一組名詞。

→ `se-context-language`、`rules/register.md`

### 8. 借用既有語彙，不自創詞

任務分解整套用作業系統併發模型命名：Process、Thread、Coroutine、Mutex、Ready Queue、GIL。

理由不是好聽：這些詞在模型的預訓練裡已有豐富先驗。**你已經知道兩個 thread 同時寫同一塊記憶體會出事**——那份直覺不用重新教。自創的詞徵召不到任何先驗，你要花定義的 token 去買別人免費送的東西。

同時它讓一個常見錯誤變得顯眼：**寫入衝突是 mutex，不是依賴**。標成 `Depends on` 會憑空製造一條假的關鍵路徑。

→ `.claude/EXECUTION_MODEL.md`

### 9. 人的決策是全域鎖

一次丟三個問題給人，等於三個都卡住。

所以：能自己查的**事實**自己查，只把**決策**交出去；一次一個，附推薦答案與代價；發現多個缺口時只問「猜錯要重做」的那些，其餘宣告假設往下走。

→ `rules/dispatch.md` 第 4 條

### 10. 每一輪留下可檢索的領悟，而且要有升級路徑

沒有升級路徑的帳本只是日記；沒有帳本的常駐規則沒有證據。

```
機遇（撞到）→ 領悟（寫成 Lesson）→ 智慧（升級成常駐規則）
```

一則 Lesson 被召回並確實有用 3 次以上，它就不是偶然而是規律，該升級成 `rules/`、Skill 或 ADR——而且升級時它本身就是 ABLATION 要求的失敗證據。

**這是這套配置和一般開發配置唯一的結構性差別。**

→ `se-epiphany`

## 為什麼是這些元件

| 元件 | 解決什麼 | 不做什麼 |
|---|---|---|
| `rules/`（6 條） | 每次工作都成立、而且與模型預設行為不同的約束 | 不放方法論——那會讓常駐面爆炸 |
| `skills/`（16 個） | 按需載入的方法庫 | 不放不變的鐵律——那該常駐 |
| `agents/`（10 個） | 需要 context 隔離、權限邊界或第二意見時的派發模板 | 不放 Skill 的知識——重複的知識會漂 |
| `docs/lessons/` | 跨輪、跨專案的長期記憶 | 不放待辦——那進 issue tracker |
| `.out-of-scope/` | 被拒絕過的機制與理由 | 不是垃圾桶，是決策的記憶 |

### 為什麼 Skills 厚、Runtime 薄

常駐面越大，模型每一輪要處理的約束越多，而且**大部分約束跟當下這個任務無關**。

按需載入的代價只有一行指標（skill 的 description），而收益是「用到才付」。所以：不變的鐵律常駐，其餘全部下放。

判準一句：**每次任務都必須遵守，而且與模型預設行為不同嗎？** 兩個條件缺一，就是 Skill。

## 刻意不做的事

拒絕也要有紀錄，否則同一個提案會反覆出現。

| 不做 | 理由 |
|---|---|
| **需求追溯主鏈、簽核硬閘、Excel 追蹤簿** | 那是可稽核交付的成本結構。個人與小團隊的快速迭代付不起，也不需要。真的需要時是另一條線，不是把它塞進這條 |
| **大量 slash command 與 output style** | 為弱模型寫的鷹架。在前緣模型上壓縮解空間、製造規則間的猶豫 |
| **把每次對話摘要寫成專案內的影子文件** | 暫態狀態交給平台的 session/task 機制。值得長期保存的進 Lesson、ADR 或測試證據 |
| **把外部 CLI 包成 wrapper 層** | 只路由、不重新想像。包裝層會在上游改版時變成負債 |
| **自動安裝系統依賴** | 預設只檢查不改系統。改系統要明確授權 |
| **讓兩個 Reviewer 互相參照** | 首輪獨立性是雙軸 review 的全部價值 |
| **用第三個模型對爭議投票** | 投票不是證據。要的是能辨別爭議的最小測試 |
| **沒在本地跑過的 benchmark 數字** | 寫進文件就會被當成已確認。這違反第 1 條信念 |
| **把知識庫塞進 skill** | Skill 放**操作流程**，知識留在筆記裡。流程會被反覆執行，知識只會偶爾查——把知識常駐是最貴的做法 |

要重新提案上述任何一項，先讀這一節，並在 `.claude/.out-of-scope/` 留一份新的評估。

## 兩個特例領域

系統設計與 ML 是**遇到相關問題才觸發**的專門流程，不是每個專案都會用到。它們有自己的階段與 Gate，因為這兩個領域的失敗模式很特殊：

| 領域 | 特殊在哪 | 對應 |
|---|---|---|
| **系統設計** | 最常見的失敗是「還沒估算就開始擺元件」與「每個都講一點、沒有一個講深」。所以強制先量化、強制挑 2–3 個瓶頸深挖 | `se-system-design`、`thread-system-architect` |
| **ML** | 最常見的失敗是「驗證設計錯了，但分數很漂亮」。所以優先序把 split 與 leakage 排在模型與調參之前，而且 Gate 沒過不准往下 | `se-ml-lifecycle`、`process-ml-engineer`、`thread-ml-auditor` |
| **ML 可解釋性** | 第二常見的失敗是**把「模型依賴 X」寫成「X 造成 Y」**——這是信念 1 在 ML 場景的具體形態。所以 Gate 3F 要求量化 rank stability，並禁止未標記的因果措辭 | `se-ml-lifecycle` Stage 6、`thread-ml-interpreter` |

兩者共通：**不能出錯的部分用 Gate 或檢查表保證（信念 2），每個結論帶證據等級（信念 1）。**

## 這份文件怎麼維護

- 新增一條常駐規則 → 在 ABLATION 登記失敗證據，**不必**在這裡加一節（除非它改變了某條核心信念）。
- 拒絕一個機制 → 在「刻意不做的事」加一列，並在 `.out-of-scope/` 留檔。
- 某條信念被實戰推翻 → **改它，並寫一則 Lesson 記錄推翻的過程**。信念被推翻不是失敗，是這套配置在運作的證據。
